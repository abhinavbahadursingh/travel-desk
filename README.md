# Travel Agent

AI-powered internal corporate travel management. Employees plan and request trips through a web
dashboard or a Slack slash command; managers approve the requests routed to them; travel operations
confirm real bookings; super admins manage accounts, roles and policy. Itineraries are drafted from
**real-time web search** and the app only ever surfaces **outbound booking links** to real provider
sites — it never simulates a transaction.

**Stack:** Next.js 15 (App Router) · TypeScript · Tailwind · Prisma + SQLite (dev; one-line switch to
Postgres) · **Groq** (AI reasoning, default `llama-3.3-70b-versatile`, override via `GROQ_MODEL`) ·
**Tavily** (primary real-time web search) · **Google Maps Routes API** (optional, for real cab
routing).

See [`plan.md`](./plan.md) for the build plan and status and [`WORKING.md`](./WORKING.md) for the
current snapshot of what is implemented and verified.

## Strict data policy

- No mock GDS, no dummy inventory, no fabricated prices, no simulated availability.
- No seeded demo trips, users, bookings, approvals or sample records. The only account the seed
  creates is the local identity you configure through `DEV_USER_EMAIL`; the only other seeded record
  is the travel policy.
- Every candidate carries its **source hostname** and **retrieval timestamp**.
- Every candidate also carries a `priceType` and an `availabilityStatus`:
  - `priceType` is `listed`, `indicative`, `verified` or `unavailable`.
    `listed` means "appeared in a public search listing"; `indicative` means
    either the source hinted at indicative language (`from`, `starting at`,
    `approx`, `average`, …) or the amount was converted into the trip
    currency via a live FX rate; `verified` is only emitted when a travel
    admin records a real provider confirmation reference; `unavailable`
    means no reliable price. Tavily snippets never produce `verified`.
  - `availabilityStatus` is `unverified`, `available_verified` or
    `unavailable_verified`. Tavily listings and Google Maps route lookups
    stay `unverified`; the verified variants are only written on
    travel-admin confirmation.
- Trip-level estimated cost is nullable: when any featured leg lacks a
  listed price, the stored `estimatedCost` is `NULL` and every surface
  (dashboard, trips list, approvals, trip detail, Slack, AI chat/compare,
  reports) renders "Total cost unavailable — some prices are missing."
  instead of a fabricated zero. Financial reports exclude unknown costs
  from numerical totals and expose a `missingCosts` count per grouping.
- Currency conversion uses a live FX feed (open.er-api.com) with a 6h TTL
  and a hard 24h staleness ceiling. No hardcoded static fallback: if the
  live rate is unavailable and no sufficiently-fresh snapshot exists, the
  app preserves the original currency and tells the user. Every converted
  amount carries `rateSource` and `fetchedAt`.
- Prices are reported only when parsed from the source — otherwise the UI shows the explicit
  "Price unavailable" badge and the policy engine raises `PRICE_UNVERIFIED`.
- If the search backend is unreachable, the plan API returns `503` with
  `{ status: "unavailable", reason, retrievedAt }` and the UI shows a search-unavailable banner. The
  app never falls back to mock data.
- Groq is used only for reasoning over retrieved results (comparison, policy explanation, follow-up
  chat, structured extraction of trip fields from freeform Slack text). It is never asked to invent
  listings, flight numbers, hotel names, train numbers, prices or availability.
- Booking confirmation requires a **real provider reference** typed by a travel admin or super admin.
  No reference is ever generated by the app.

## Roles and permissions

Authorization is enforced **server-side only**. The browser never supplies a role; every API resolves
the caller from `DEV_USER_EMAIL` and the database, and inactive accounts are refused.

| Role | Can do |
|---|---|
| `employee` | Create/edit own drafts, plan real search, submit, track approval, view booking links and own bookings, request cancellation. Never approves, never sees another employee's private trip, never confirms bookings, cannot change their own role or policy. |
| `manager` | Everything an employee can, plus an approval inbox limited to approvals assigned to them, reporting employees, decisions with mandatory rejection reasons, change requests and comments. Cannot approve unassigned requests or change company policy. |
| `travel_admin` | Everything an employee can, plus all trips, booking operations and real reference recording, cancellation review, approval overview and reassignment, employee directory and reports. |
| `super_admin` | Everything a travel admin can, plus user accounts, role and reporting-manager management, policy configuration, audit log, system health and application settings. |

### Approval resolution order

When a request needs a decision (employees always do), the app picks the first eligible approver:

1. the requester's assigned manager (`User.managerId`);
2. an active manager in the requester's department;
3. an active travel admin;
4. an active super admin.

An approver must be **active**, must **not be the requester**, and must have an approver role. If no
eligible approver exists, submission returns `409` with an actionable message and no approval row is
created — an employee request is never silently auto-approved. Managers, travel admins and super
admins may auto-approve only when policy passes, the estimate is complete and the policy switch
allows it.

### Trip lifecycle

```
draft ──plan──► draft ──submit──► pending_approval ──approve──► approved
                                        │                          │
                                        ├─reject──► rejected       └─generate links──► booking_links_generated
                                        └─request changes──► draft          │
                                                                            └─record references──► booking_pending_confirmation
                                                                                      │
                                                                                      └─all legs confirmed──► booked
                                                                                                                │
                                                                                            request cancellation ─┘
                                                                                                                ▼
                                                                                                     cancellation_requested
                                                                                                       ├─reject──► booked
                                                                                                       └─verified reference──► cancelled
```

Planning never implies approval. Approval never implies booking. Opening a provider link never
changes state. A cancellation request never cancels anything; only a verified admin completion with a
real provider cancellation reference moves the trip to `cancelled`.

### Booking leg states

Every generated booking category (flight, hotel, train, cab) is a booking leg:

| State | Meaning |
|---|---|
| `pending` | Booking link generated; awaiting external action or admin confirmation. Legacy stored value: `link_only`. |
| `booked` | Booked on the real provider; a travel admin recorded a real confirmation reference. Legacy stored value: `manually_confirmed`. |
| `not_required` | The category was marked unnecessary (employee or travel ops); exempt from the booked rule. |
| `failed` | Provider booking attempt recorded as failed; blocks a required leg. |
| `cancelled` | Trip cancellation verified; booking history preserved with the provider reference. |

A trip becomes `booked` only when every **required** leg is resolved successfully; `not_required` legs
are exempt and required legs that are `pending` or `failed` keep the trip in
`booking_pending_confirmation`.

## Quick start

```bash
# 1. install
npm install

# 2. env — copy and fill in:
#    GROQ_API_KEY         (get one at https://console.groq.com)
#    TAVILY_API_KEY       (get one at https://tavily.com)
#    GOOGLE_MAPS_API_KEY  (optional; enables real cab routing)
#    DEV_USER_PASSWORD    (optional; seed hashes and stores it for the account)
cp .env.example .env

# 3. generate client + create SQLite DB + local account/policy (and either
#    hash DEV_USER_PASSWORD or print a one-time activation token)
npm run setup

# 4. run
npm run dev
```

Open http://localhost:3000. `npm run dev` is pinned to port 3000. Do not start a second dev server
against the same `.next` directory — use `NEXT_DIST_DIR` if you need an isolated build directory.

### Local account & signing in

The seed creates exactly one account, from `.env`:

- `DEV_USER_EMAIL` — required; the account you sign in as.
- `DEV_USER_NAME` — defaults to the email prefix.
- `DEV_USER_ROLE` — `employee`, `manager`, `travel_admin` or `super_admin` (default `travel_admin`).
  The seed sets the role only when creating the account; afterwards roles are managed by a super
  admin from **User management**, so re-running the seed cannot escalate an existing account.
- `DEV_USER_DEPARTMENT` — optional; used for departmental approval routing.
- `DEV_SLACK_USER_ID` — optional; your real Slack member ID for `/travel`.
- `DEV_USER_PASSWORD` — optional. If set, the seed hashes it and stores it so you can sign in
  immediately at `/login`. If omitted, the seed prints a one-time **activation token** (24h TTL)
  that you redeem at `/activate` to set a password. The seed never overwrites an existing password.

Authentication now uses an HttpOnly session cookie and a double-submit CSRF cookie. Sessions are
server-side rows in `Session` and store only `sha256(rawToken)`. The CSRF cookie is auto-mirrored
to the `X-CSRF-Token` header on every state-changing request by `components/CsrfFetchBridge.tsx`;
existing client components did not need to change. Failed logins are rate-limited (5 attempts →
15-minute lockout).

To add more users, use the super-admin **User management** page or Prisma Studio, then issue each
new account a reset token via `POST /api/admin/users/[id]/reset-password` (returns a one-time
activation URL you hand to the user).

`ALLOW_DEV_IDENTITY=1` is an **escape hatch**: it lets `getCurrentUser()` fall back to
`DEV_USER_EMAIL` when there's no session, so local scripts and the middleware short-circuit for
dev convenience. Leave it unset in anything resembling production.

## End-to-end walkthrough

1. **Create the request:** *New request* → purpose + route + dates + cabin. The planner searches
   flights, hotels, trains and cabs in parallel and stores candidates with source + retrieval time.
2. **Submit for approval:** employees always go to an independent approver. Managers/admins may
   auto-approve within policy and with a complete estimate. No eligible approver → actionable `409`.
3. **Manager decision:** the approver can comment, request changes (trips return to `draft` with the
   history preserved), reject with a mandatory reason, or approve. Decisions are transactional —
   double decisions return `409`.
4. **Booking links:** once approved, *Get booking links* materialises featured + alternate candidates
   as `Booking` rows with `status: "link_only"`. Opening a link never changes state.
5. **Record real references:** a travel admin enters the real provider confirmation per leg. One leg
   → `booking_pending_confirmation`; all legs → `booked`.
6. **Cancellation:** the requester asks to cancel (`cancellation_requested`). Travel operations can
   reject (back to `booked`) or complete with the real cancellation reference, which marks the trip
   and its booking rows cancelled.
7. **Admin surfaces:** operations dashboard, booking queue, cancellation queue, employee directory,
   approval overview, travel reports, audit log and system health.

## Slack slash command

1. Expose your local server (e.g. `ngrok http 3000`).
2. Create a `/travel` slash command pointing at `https://<your-tunnel>/api/slack`.
3. Put the signing secret into `SLACK_SIGNING_SECRET` in `.env`.
4. Set `DEV_SLACK_USER_ID` and run `npm run db:seed` so `/travel` can match your local account.

```
/travel plan Berlin 2026-11-18 to 2026-11-20 for Q4 review
/travel status
/travel approve <trip id>
/travel reject <trip id> <reason>
/travel help
```

Slack decisions go through the same transactional decision service as the dashboard: only the
assigned approver (or a travel/super admin) can decide, the requester can never approve their own
trip, and a rejection requires a reason. Trips created from Slack start as drafts; submit them from
the dashboard.

| `GET /api/approvals` | Inbox / history / all, scoped by role |
| `POST /api/approvals/[id]` | Approve, reject (reason required) or request changes |
| `POST /api/approvals/[id]/comments` | Comment / clarification thread |
| `POST /api/approvals/[id]/reassign` | Travel ops: reassign a pending approval |
| `GET /api/cancellations`, `POST /api/cancellations/[id]` | Cancellation queue and review |
| `GET/PATCH /api/notifications` | Inbox and read state |
| `GET/POST /api/admin/users`, `PATCH /api/admin/users/[id]` | Super admin account/role/manager management |
| `GET/PATCH /api/admin/policy` | Policy view (travel ops) and configuration (super admin) |

or state conflict with an actionable message, `502/503` upstream provider failures.

### Testing

- Every automated test runs against an isolated `prisma/test.db`; `prisma/dev.db`
  is never touched. The provisioner (`tests/setup/global-setup.ts`) asserts
  that `DATABASE_URL` resolves to a `test.db` path and refuses to run otherwise.
- The Playwright `webServer` starts Next on port 3100 with
  `NEXT_DIST_DIR=.next-e2e`, so you can keep `npm run dev` running on port 3000
  during E2E runs without a route-manifest collision.
- External providers (Groq, Tavily, Google Maps, Slack) are blanked for the
  test environment; no outbound calls happen in CI.
- Tests cover: policy evaluation, approver resolution, booking/cancellation
  lifecycle transitions, cost/currency math, search normalization, trip CRUD
  via the real route handlers, trip-access/CSRF/role-restricted security
  regressions, session-rotation + session-revocation on deactivation/role
  change, dev-identity hardening in production, and three Playwright smoke
  specs for the role dashboards.

### Outbound notifications (email + Slack)

The app persists every workflow event as an in-app notification and, when
configured, queues it for external delivery through a transactional
outbox (`NotificationDelivery`).

- `RESEND_API_KEY` + `EMAIL_FROM` enable email via Resend.
- `SLACK_BOT_TOKEN` enables DMs to `User.slackUserId` via
  `chat.postMessage`; `SLACK_WEBHOOK_URL` is the channel-broadcast
  fallback used for admin events and recipients with no Slack id.
- `APP_BASE_URL` is embedded in outbound links.

If none of these are set, delivery is a safe no-op: in-app notifications
continue to work and no "stuck failed" rows pile up.

Operators can drain the outbox manually with
`POST /api/admin/notifications/process` (super-admin only); each
state-changing route also fires a non-blocking drain after commit.

### Production environment

- `NODE_ENV=production` must be set in real deployments. When it is:
  - `ALLOW_DEV_IDENTITY=1` / `DEV_USER_EMAIL` are **hard-disabled**. Any
    request with no valid session cookie is rejected as unauthenticated,
    regardless of what those env vars resolve to.
  - `lib/env.ts::assertProductionEnv()` runs on cold boot and logs a line
    per misconfiguration (`DATABASE_URL` missing or pointing at the test DB,
    the dev-identity flag leaking into the environment, etc.).

## Switching to Postgres

Phase 4 ships a production-grade PostgreSQL path alongside the SQLite dev
default. Both schemas carry the same models; each has its own migration
history and generated Prisma client, so switching is a config change, not
a code change.

| Workflow | SQLite (default) | PostgreSQL |
| --- | --- | --- |
| Schema file | `prisma/schema.prisma` | `prisma/schema.postgres.prisma` |
| Migrations | `prisma db push` from `schema.prisma` | `prisma/migrations/*` applied via `prisma migrate deploy` |
| Generated client | `@prisma/client` (default output) | `@prisma/client-postgres` (separate output) |
| Apply schema | `npm run db:push` | `npm run db:pg:migrate:deploy` |

### One-time Postgres provisioning

1. Create the database. Example for local Homebrew Postgres:
   ```bash
   createdb travel_agent
   ```
2. Apply the Postgres schema:
   ```bash
   DATABASE_URL="postgresql://user:pass@host:5432/travel_agent" \
     npm run db:pg:migrate:deploy
   ```
3. Point `DATABASE_URL` in `.env` at the same URL and run
   `npm run db:seed` to insert your local account + travel policy.

### One-shot data migration from local SQLite

The repo also ships a utility that walks every table in `prisma/dev.db`,
upserts each row into Postgres by primary id, and refuses to continue
when source/destination counts disagree. It takes a backup of `dev.db`
first (into `prisma/backup/dev-<iso>.db` with the matching `-wal`/`-shm`
files when present) and never mutates the source.

```bash
# target must already have the Postgres schema applied
SQLITE_URL="file:./prisma/dev.db" \
POSTGRES_URL="postgresql://user:pass@host:5432/travel_agent" \
  npm run db:migrate:from-sqlite
```

Re-running the utility is safe: every write is an `upsert`, so a partial
previous run settles into the same end state.

### Postgres concurrency & integrity tests

`tests/integration/postgres-concurrency.test.ts` pins the invariants that
only matter under a real MVCC engine: unique-constraint behaviour on the
outbox `dedupeKey`, race-free pending approvals, lifecycle `updateMany`
guards, transaction rollback through the outbox, and the `SELECT … FOR
UPDATE SKIP LOCKED` primitive that the outbox drainer uses in HA mode.
Opt in with:

```bash
POSTGRES_TEST_URL="postgresql://user@host:5432/travel_agent_test" npm run test
```

Without the env var the suite is skipped and the SQLite tests run as
usual.

## Search providers

| Provider | What it powers | When it's used |
|---|---|---|
| **Tavily** | flights, hotels, trains, cabs | always — the primary real-time web search |
| **Google Maps Routes API** | cabs only — real distance + duration | when `GOOGLE_MAPS_API_KEY` is set |
| **Open-Meteo geocoding** | origin/destination typeahead suggestions | while typing 2+ characters — real GeoNames place records, no API key |

`lib/search.ts` is isolated — swap Tavily for Brave / Bing / SerpAPI by implementing a new `*Search`
adapter alongside `tavilySearch` and routing to it from `runWebSearch`. The exported
`searchFlights/Hotels/Trains/Cabs` signatures are the contract.

### Result shape (every search candidate)

| field | meaning |
|---|---|
| `title` | headline the source showed |
| `category` | `flight` / `hotel` / `train` / `cab` |
| `source`, `sourceHostname` | hostname of the provider site |
| `sourceUrl` | deep link to the provider |
| `description` | short snippet from the source |
| `price`, `currency` | parsed from the snippet only, else `null` |
| `priceType` | `listed` when parsed, `unavailable` when not |
| `availabilityStatus` | `listed` (Google Maps route), `unverified` (Tavily listing), or `unavailable` |
| `retrievedAt` | ISO timestamp of the retrieval |
| `rankScore` *(v2.d)* | 0–100 weighted score — Phase 5 reweight: price 22% · policy 15% · direction 18% · date 12% · reliability 15% · duration 10% · freshness 8% |
| `rankReasons` *(v2.d)* | plain-text reasons shown on the chip tooltip |
| `priceDelta`, `isCheapest`, `isMostExpensive` *(v2.d)* | cross-candidate comparison within the same category |
| `reliability` *(v2.d)* | `verified` (on the per-category allowlist), `general`, or `unknown` |
| `freshness` *(Phase 5)* | `fresh` (<30 min), `aging` (30 min–2 h), `stale` (>2 h). The legacy `isStale` boolean is still exposed. |
| `directionMatch` *(Phase 5)* | `match`, `reversed`, or `unknown`. A reversed candidate is never featured when a non-reversed alternative exists. |
| `dateMatch` *(Phase 5)* | `match`, `mismatch`, or `unknown` — snippet date compared against the trip depart date within ±3 days. |
| `matchConfidence` *(Phase 5)* | `high` / `medium` / `low` — combines direction, date, reliability and freshness. `reversed` or `mismatch` forces `low`. |
| `durationMinutes` *(v2.d)* | parsed from the snippet when the source states a travel time; `null` otherwise — never fabricated |

### Trains — Indian railway priority

Train searches detect Indian cities in origin / destination and prioritise `irctc.co.in`,
`indianrail.gov.in`, `trainman.in`, `ixigo.com`, `confirmtkt.com`, `railyatri.in`, `erail.in` ahead
of international rail sites.

### Decision engine (v2.d)

`POST /api/trips/[id]/compare` with `{ question }` runs the Groq comparison helper over the
ranked featured candidates and per-category summaries already stored for the trip — never the
raw itinerary JSON. The trip detail page exposes it as a *Decision engine* card with quick
questions: *train or flight · cheapest · time · best fits policy*. The helper only reasons over
retrieved data; it never invents listings, prices or availability.

### Currency (v2.d)

FX conversion uses a live rate from `open.er-api.com` (6h in-memory cache). On failure the
server falls back to the previous static table; if both fail, candidates stay in their original
currency and the UI discloses `converted from <currency> <amount>`. Set `INR_PER_USD` in `.env` to
override the fallback INR rate.
